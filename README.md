# Python Data Playground

A learning environment for Python data analytics and APIs, built around one idea:
**you do not learn to write algorithms by reading them.**

Every lab comes in two halves. The first is a worked example — fully implemented,
commented line by line, explaining not just what it does but why it is done that
way. The second is a *twin exercise*: the same technique, a different dataset, a
complete specification, and a stub that raises `NotImplementedError` until you
fill it in. A pytest suite grades it.

The exercises fail on a fresh clone. That is the starting line, not a bug.

---

## Quickstart

**Windows (PowerShell):**

```powershell
py -3.12 -m venv .venv; .\.venv\Scripts\Activate.ps1; pip install -r requirements.txt
```

**macOS / Linux:**

```bash
python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
```

Then confirm the environment is healthy — the 40 worked-example tests should pass
and the 89 exercise tests should fail:

```bash
pytest
```

And start the playground:

```bash
python -m uvicorn app.main:app --reload
```

Open <http://127.0.0.1:8000>. The generated API documentation is at
<http://127.0.0.1:8000/docs>.

## How to work through it

1. **Pick a lab** in the sidebar. Lab 01 assumes nothing beyond basic Python.
2. **Read the worked example** — in the browser, or better, in your editor. The
   module docstring explains the concept and the traps; the function body is
   commented throughout.
3. **Open the lab file and implement the exercise.** The docstring is a full
   specification: arguments, return shape, dtypes, edge cases, and hints naming
   the specific methods to reach for.
4. **Run the tests.** Either the button in the UI, or:
   ```bash
   pytest tests/test_lab01.py -v
   ```
5. **Read the failures.** They are written to tell you what is wrong and often
   why the wrong answer is tempting.

Useful selectors:

```bash
pytest -m demo        # only worked examples — a health check on your environment
pytest -m exercise    # only your work — your progress bar
pytest tests/test_lab07.py::TestRegionQueryValidation -v   # one group
```

| Panel | What it gives you |
| --- | --- |
| **Labs** | Concept, both function names, the full source, the test suite, and a Run button with per-test results |

## The data

Three synthetic CSVs in `data/`, generated by `scripts/generate_data.py` from a
fixed seed. Synthetic, but not random noise — there is real structure to find:

- **`orders.csv`** (2,931 rows) — a year of orders. Deliberately messy: 74 blank
  `units`, 12 exact duplicate rows, and one channel spelled eight different ways.
  Regions differ in basket size and seasonal products really are seasonal.
- **`customers.csv`** (400 rows) — regions, segments, signup dates. Six customers
  never ordered, which is what makes lab 04's join direction matter.
- **`sensor.csv`** (2,160 rows) — 90 days of hourly readings with a 24-hour cycle,
  a seasonal drift, 39 dropped readings and one deliberate 7-hour outage.

The data is committed, so you never need to generate it. To change or regenerate it:

```bash
python scripts/generate_data.py
```

## Why there is no scikit-learn

Lab 08 asks you to write the confusion matrix, precision, recall, F1 and AUC
yourself, in numpy. `roc_auc_score(y, p)` is one line and teaches you nothing
about what AUC measures; implementing it once means you will never again misread
a model report.

There is also a practical reason. On the Windows machine this repo was built on,
Smart App Control blocks scipy's unsigned native DLLs, so `import sklearn` dies
with `DLL load failed while importing _dierckx`. scikit-learn depends on scipy,
and the only workaround is disabling a security feature that cannot be re-enabled
without reinstalling Windows. Not worth it — and the hand-written version is the
better exercise anyway.

Once lab 08 passes, installing scikit-learn on a machine that allows it and
checking your numbers against `sklearn.metrics` is an excellent next step. See
[docs/going-further.md](docs/going-further.md).

## Project layout

```
labs/            One module per lab: worked example + exercise stub
  __init__.py      Dataset loaders. load_clean_orders() is the lab 01 reference answer
  registry.py      The lab catalogue the UI reads
tests/           One pytest file per lab. These are the specification
data/            Three committed CSVs
scripts/         Data generator and two runnable demos
app/             The FastAPI playground server
  main.py          Routes: labs, datasets, scratchpad, live analytics endpoints
  runner.py        Runs pytest in a subprocess and parses the result
  pytest_report_plugin.py   A small pytest plugin that emits JSON for the UI
  static/          The front end — plain HTML, CSS and JS, no build step
docs/            Longer-form notes
```

## Adding your own lab

1. Write `labs/lab09_yourthing.py` with a worked function and a stub.
2. Write `tests/test_lab09.py`, marking tests `@pytest.mark.demo` or
   `@pytest.mark.exercise`.
3. Append a `Lab(...)` entry to `labs/registry.py`.

The UI picks it up on the next page load. There is nothing else to register.

## A note on the scratchpad

`/api/scratch` executes Python you type, in a subprocess, with your permissions.
That is the entire point of a scratchpad and it is perfectly safe while the server
is bound to `127.0.0.1` — nothing outside your machine can reach it.

**Do not bind this server to `0.0.0.0`, expose it through a tunnel, or deploy it.**
It is a local learning tool, not an application.
